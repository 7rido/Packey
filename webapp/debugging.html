Debugging a silent API change: when HTTP 200 lies

Alfrido Phagoo

I run a package-tracking service that reads shipment status from several carrier APIs (17TRACK, USPS, OnTrac, and a paid fallback). One day, tracking stopped updating for a group of packages — but nothing in my logs said "error." Every request was returning HTTP 200.

The symptom

Valid tracking numbers that had worked the day before came back with empty status fields. No error code, no failed request, no rate-limit warning. Just 200 OK with nothing useful inside.

How I investigated

  1. Reproduced it outside the app. I took a known-good tracking number and sent the same request by hand with curl, so I could see the raw response instead of my app's parsed version.
  2. Compared it to a working case. I put the broken response next to a good one from a different package. Same endpoint, same authentication, same headers — the difference was in the body.
  3. Isolated the cause. The provider had changed the shape of its response: a field my code expected had moved, so my parser silently read nothing. The request was fine; my assumption about the response was not.

The fix

  • Added validation. If a response is 200 but the required fields are missing, treat it as a failure instead of a success.
  • Added a fallback. When the primary source returns nothing usable, try the next source so tracking keeps working.
  • Wrote it down. Documented the symptom and the fix so the same silent failure would be recognized faster next time.

What I took from it

200 OK is not the same as "working." A healthy request can still return a useless body, and a good integration checks the content, not just the status code. That habit — reproduce with a raw request, compare to a known-good case, fix the cause, write it up — is how I approach any integration problem, and it is the core of technical support.
